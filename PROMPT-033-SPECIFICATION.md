# PROMPT-033 — Notification & Document Generation Framework

**Document type:** Development specification & implementation plan (per §42 — same pattern as PROMPT-030/031/032: no "implement" instruction, no "STOP before PROMPT-034" directive; §43's own Definition of Done is spec-readiness framed). **No application code was written for this deliverable.**

**Baseline used:** the actual current codebase after PROMPT-001–032 (030/031/032 were also spec-only). Verified by direct inspection of every existing print-preview implementation (`PurchaseOrderManagement.tsx`/`GoodsReceiptManagement.tsx`/`PurchaseInvoiceManagement.tsx`/`PurchaseReturnManagement.tsx`), `app/models/sales_invoice.py`, `app/models/einvoice.py`, `app/models/payroll_record.py`, `context/ToastContext.tsx`, `package.json` (frontend dependency list), and PROMPT-030/031/032-SPECIFICATION.md (cross-referenced, not re-derived).

---

## 1. Requirement Understanding

PROMPT-033 asks for a centralized document-generation and notification framework spanning every module. The grounding research surfaces a critical, previously-undiscovered fact: **this codebase's existing "document generation" is entirely client-side, on-demand, browser-print-based — there is no PDF library anywhere in `package.json`, no server-side rendering, and no persisted document artifact of any kind.** The 4 existing `PrintPreviewModal`-style components (Purchase Order/Goods Receipt/Purchase Invoice/Purchase Return, PROMPT-020-023) each render the ALREADY-FETCHED detail object into print-friendly HTML and call the browser's native `window.print()` — no PDF bytes are ever generated by this application; the OS/browser print dialog produces the PDF (e.g. via "Save as PDF"), if one is produced at all.

The second critical finding, directly bearing on §6 (Historical Document Integrity): **`sales_invoice` captures `customer_gstin` but NOT `customer_name`/`customer_address` as a snapshot — these are read live via the `customer_id` FK join at render time — and NO tenant/seller identity snapshot exists anywhere.** This means a customer name edit or a tenant business-profile change TODAY would silently change how every past invoice prints, violating §6's own core principle. **PROMPT-029's Payroll module already solved this correctly** (`payroll_record.employee_code_snapshot`/`employee_name_snapshot`/`designation_snapshot`, frozen at calculation time) — this spec's central recommendation is to apply that SAME already-proven pattern to Sales/Purchase documents, not invent a new one.

## 2. Objective

Design a centralized `DocumentService` + `NotificationService` layer that (a) generates print-ready, browser-rendered documents from authoritative transaction data (reusing the existing print-preview pattern's PHILOSOPHY, not its per-module duplication), (b) closes the historical-integrity gap via snapshot columns, and (c) introduces the first PERSISTED, queryable in-app notification mechanism this codebase has ever had (today's `ToastContext` is ephemeral, single-message, session-only — not a notification system in the sense this prompt means).

## 3. Scope

- A `document` metadata table + `DocumentService` — generation is ON-DEMAND/browser-rendered for M1 (no server-side PDF engine is introduced, see §12/Open Decisions), but generation EVENTS and their outcomes are tracked centrally.
- Snapshot columns for Sales Invoice / Purchase Invoice (and, by the same reasoning, their correcting documents — Sales/Purchase Return, Credit/Debit Note) closing the §6 gap, mirroring PROMPT-029's `payroll_record` pattern.
- A reusable, shared print-template SHELL (React component + shared print CSS) that the 4 existing per-document print components migrate onto, plus new ones for Sales Estimate/Sales Order/Delivery Challan/Sales Invoice/Sales Return/Credit-Debit Note/Customer Receipt/Supplier Payment/Payslip (currently NONE of these Sales/Payment/Payroll documents have ANY print view at all — confirmed, only the 4 Purchase-side documents do).
- A `notification` table + `NotificationService` + `GET /api/v1/notifications` — the first real, persisted, per-user notification center this codebase has had.
- Report export stays JSON-only for M1 (PROMPT-027's own established position, reaffirmed not re-litigated) — PDF/Excel export for reports is Open Decision #8/#9, not built.

## 4. Out of Scope

- A true server-side PDF-rendering engine (wkhtmltopdf/Puppeteer/WeasyPrint-style) — no such infrastructure exists, none is added here (Open Decision #8, "whether PDF is mandatory for every document" — resolved as "browser-print-generated, not server-generated" for M1).
- Object/file storage (S3-style) — no persisted PDF BYTES exist to store; only metadata is persisted (§14/§16 below explain why).
- Email/SMS/WhatsApp/Push notification channels — explicitly excluded per §23's own instruction ("do not add… unless explicitly approved"); IN_APP is the only channel enabled in M1.
- Tenant logo upload / visual template customization — no such capability exists or is added (Open Decision #6/#7).
- Digital signatures, watermarking, document passwords/encryption — none approved anywhere in this codebase's source documents (Open Decision #19/#22/#23).
- Rebuilding Reports' own calculation engine — report export, where it exists, calls the SAME `app/services/reports/*.py` methods the screen itself calls (PROMPT-027's own "Dashboard KPIs reconciled by construction" discipline, extended here to exports).

## 7. Document Lifecycle

Given M1's on-demand, browser-rendered architecture (§4), the source prompt's own two lifecycle shapes are RECONCILED, not both built in full:

```
Transaction
   ↓
Validated / Posted / Finalized      (already true — every document type's own status machine)
   ↓
Document Generation Requested        (user clicks "Print Preview" / "Download")
   ↓
Template Resolved                    (client-side: DocumentType → React print component)
   ↓
Authoritative Data Loaded            (the SAME GET /{entity}/{id} the detail screen already called —
                                       no separate "document data" fetch)
   ↓
Document Generated                   (browser renders the print-CSS'd HTML)
   ↓
Document Available                   (immediately — synchronous, no job queue for M1)
   ↓
Preview / Download / Print           (window.print(); "download" = the browser's own
                                       Save-as-PDF from the print dialog)
```

**The asynchronous REQUESTED→PROCESSING→COMPLETED/FAILED→RETRY lifecycle is NOT built for M1** — there is no background-job infrastructure anywhere in this codebase (the same confirmed absence PROMPT-018/028/031 each independently found), and browser-rendered generation is synchronous by nature (it either renders or it doesn't, in milliseconds, on the client). This is Open Decision #24, resolved here as "synchronous for all document types in M1," not silently assumed — a future server-side PDF engine (if ever added) would be the trigger to revisit this.

## 8. Authoritative Data Model

For every document type, the print component receives EXACTLY the same detail object its own screen's `GET /{entity}/{id}` endpoint already returns — **no second, parallel "document data" fetch or transformation layer is introduced**. This is already how the 4 existing Purchase-side print components work (verified: `PrintPreviewModal`'s own prop is `order: PurchaseOrderDetail`, the identical type the detail modal uses) — this spec formalizes that pattern as the MANDATORY approach for every new print component, closing off any temptation for a future developer to "helpfully" recompute a total inside a print component.

## 9. Historical Document Integrity

**This is the spec's central, highest-priority recommendation**, directly addressing the gap found in §1.

### 9.1 The gap, precisely

| Field | Currently snapshotted? | Risk |
|---|---|---|
| `sales_invoice.customer_gstin` | **Yes** (already a column) | None |
| Customer name/address | **No** — read live via `customer_id` join | A customer name/address edit changes how EVERY past invoice for that customer renders |
| Seller (tenant) name/address/GSTIN | **No** — read live via `currentTenant` (frontend) / would be a live `tenant` table join (backend) | A tenant business-profile edit changes how EVERY past document for that tenant renders — the MORE severe of the two, since it affects the tenant's OWN legal identity on every historical GST document |
| Line item description/HSN/rate | **Partially** — `sales_invoice_line` stores its own `unit_price`/`discount`/`hsn_code`/`gst_rate` at posting time already (confirmed, PROMPT-015's own design) — this part is ALREADY correct | None |
| Place of supply | **Yes** — `place_of_supply_state_code` is already stored on the invoice header | None |
| IRN/QR | **Yes** — `irn`/`qr_code_data` already stored | None |

So the gap is narrower than it first appears: **only the seller and buyer NAME/ADDRESS fields are missing** — everything GST-numerical (rates, amounts, HSN, place of supply, GSTIN) is already correctly frozen at transaction time. This matters for scoping the fix precisely rather than over-building.

### 9.2 The fix

New columns (additive migration), mirroring PROMPT-029's own already-proven `_snapshot` suffix convention:

On `sales_invoice`: `seller_name_snapshot`, `seller_address_snapshot`, `seller_gstin_snapshot`, `customer_name_snapshot`, `customer_address_snapshot` — populated ONCE, at invoice CREATE time (not post time — matching PROMPT-015's own "customer_gstin captured at creation" precedent already on this exact table), from `tenant.business_name`/`.address_line1`+`.city`+`.pin_code`/`.gstin` and `customer.name`/`.address` respectively. **Never updated after creation.**

The SAME pattern applies to `purchase_invoice` (buyer=tenant, seller=supplier — the mirror image) and, by the same reasoning, to every OTHER financial document type this spec adds a print view for (Sales Estimate/Order/Delivery Challan/Sales Return/Credit-Debit Note/Purchase Order/Goods Receipt/Purchase Return/Payment) — **but Payroll needs NO change**, since `payroll_record`'s own snapshot columns (PROMPT-029) already do exactly this.

**Retroactive fix for the 4 existing Purchase-side print components**: `PrintPreviewModal`'s own `businessName` prop currently comes from `currentTenant?.business_name` (the LIVE tenant context) — confirmed, this is a REAL, currently-shipping bug relative to §6's own principle, not a hypothetical. Once `purchase_order.seller_name_snapshot`-equivalent columns exist... **wait, Purchase Order's "seller" is the SUPPLIER, and the "buyer" (whose business name appears on the printed PO) is the TENANT itself** — the SAME live-tenant-profile problem applies here in reverse. This is flagged explicitly as **Requirement Conflict #1** below (§37), not silently patched, since fixing 4 already-shipped, already-tested print components is itself a small but real scope decision requiring product sign-off, not assumed automatic.

## 10. Template Architecture

A new shared component, `shared/DocumentPrintShell.tsx`, factoring out what all 4 existing (and every new) print component duplicates today: the `@media print` CSS block (hide app chrome, A4 page setup, margins), the header/footer layout skeleton (business info block, document title/number/date block, line-item table shell with repeating `<thead>` via CSS `display: table-header-group` for multi-page correctness, tax-summary block, terms/signature area). Each document type's own print component becomes a THIN consumer — passing its own header fields/line array/totals into the shell, not re-implementing the CSS.

**Legally-required values are never editable through this UI** (§7's own instruction) — the shell renders read-only data from the already-fetched detail object; there is no template EDITOR anywhere in this design (template customization is Open Decision #6, explicitly not built).

## 11. Template Versioning

**Not implemented for M1** (Open Decision #4/#21) — there is exactly ONE template per document type (the shared shell + that type's own field mapping), no versioning concept, no `template_id`/`template_version` metadata is stored. If tenant branding customization is ever approved (Open Decision #5), THAT would be the trigger to introduce real template versioning (so a historical document can be proven to have used the template active at ITS OWN generation time, not today's) — deferred, not silently built now.

## 12. PDF Generation

**No server-side PDF byte generation exists or is added.** "PDF generation" in this MVP means: browser-rendered, print-CSS'd HTML, converted to PDF by the user's own browser/OS print dialog ("Save as PDF" / a physical printer). This is a genuine, deliberate scope decision (Open Decision #8), not an oversight — it costs zero new infrastructure/dependencies and has already proven adequate for the 4 existing Purchase-side documents across PROMPT-020-023's own live-verification passes. Multi-page support, repeating headers, A4 sizing, margins are all achievable via CSS alone (the shared shell, §10) — no new library is required. Indian numbering (`₹1,23,456.78`-style grouping) — checked: **not currently implemented anywhere** (`toLocaleString()` calls found in this codebase use default/`en-IN` inconsistently — a genuine small gap, flagged for the implementation pass, not a design question).

## 13. Preview

Already correctly satisfied by the existing pattern and extended: preview and the FINAL printed output are the literal SAME React component render — there is no separate "preview renderer" to drift out of sync with the "real" one (§11's own principle, already true, being extended not re-architected). Draft/Posted/Cancelled/Reversed status is already visible via each detail object's own `status` field — the shared shell displays it as a prominent badge/watermark-style banner (e.g. a diagonal "CANCELLED" overlay for a cancelled document's print view — a small new addition, not built anywhere today, since no document currently prints at all for cancellable-after-posting types).

## 14. Printing

Reuses the existing, already-proven `@media print` discipline (hide nav via `.no-print` class, page-break control via `break-inside: avoid` on line-item rows, preserved totals/document-number/GST info since nothing is recalculated at print time — §8). No transaction data is ever mutated by opening a print view (already true — the print components are pure, read-only renderers).

## 15. Download

**"Download" in M1 = the browser's own print-dialog "Save as PDF," not a server-generated file fetched from a URL.** This SIDESTEPS the source prompt's own §13 concern entirely (no `/files/invoice/12345.pdf`-style predictable URL ever exists, because no such endpoint exists) — but it also means M1 cannot offer a true "Download" button distinct from "Print" (they're the same browser action). Flagged as Open Decision #2/#24: if genuine server-generated, independently-downloadable PDF files are later required (e.g. for emailing an invoice, which is itself excluded per §4), that would require the server-side rendering engine explicitly deferred here.

## 16. Storage

**Recommendation: A (generated on demand), not B or C** (§14 of the source prompt's own lettered options) — directly following from §12/§15: there are no PDF bytes to persist, only METADATA about generation events (§17.1). This is the SIMPLEST, lowest-risk option, and is not a compromise — it's the correct MVP choice given financial-document immutability is ALREADY guaranteed by the underlying transaction data being immutable (PROMPT-015 onward), not by a persisted file. Storing a redundant PDF copy would be pure duplication with a real integrity risk (a stored PDF could theoretically drift from the live transaction if the two were ever allowed to diverge — on-demand generation makes that structurally impossible).

## 17. Document Security

Already structurally strong by the ON-DEMAND design: every print component only ever receives data the user's own authenticated, tenant-scoped, permission-gated `GET` request already returned — there is no SEPARATE document-access control surface to get wrong, because there is no separate document-fetch endpoint at all in M1. Payroll's stricter access (`salary.view`, PROMPT-029) is inherited automatically, since the Payslip print view (once built, §21) would consume the SAME already-permission-gated payroll API.

### 17.1 Document metadata tracking (the one new persisted structure)

A new `document_generation_event` table (a deliberately NARROW, metadata-only table — NOT the source prompt's own suggested `document`/`document_template`/`document_template_version`/`document_generation_job` four-table set, most of which don't apply given the on-demand/no-versioning/no-async decisions above):

| Column | Purpose |
|---|---|
| `id` | PK |
| `tenant_id` | RLS-enabled, standard |
| `entity_type` / `entity_id` | Which transaction was printed/downloaded (e.g. `sales_invoice`, the invoice's own id) |
| `document_type` | e.g. `SALES_INVOICE_PRINT` |
| `action` | `PREVIEWED` / `PRINTED` / `DOWNLOADED` |
| `actor_user_id` | Who |
| `occurred_at` | When |
| `result` | `SUCCESS`/`FAILURE` (a client-side rendering failure, e.g. a malformed date, would be rare but possible) |

This is DELIBERATELY the smallest table that satisfies §16's auditing requirement (§18 below) without inventing template/job/storage concepts M1 doesn't use. `document`/`document_template_version`/`document_generation_job` are explicitly NOT created — flagged in Database Impact (§28) as "considered, not needed," per §32's own "do not blindly create all of these" instruction.

## 18. Document Auditing

Reuses PROMPT-031's `AuditService`/`audit_log` directly — `document_generation_event` (§17.1) is a SEPARATE, lightweight, high-volume-tolerant table (every preview/print/download is logged here), while a SUBSET of especially business-critical actions ALSO writes a proper `audit_log` entry via the existing service: specifically `DOCUMENT_DOWNLOADED` for GST-sensitive documents (Sales/Purchase Invoice, Credit/Debit Note) and Payslip — mirroring the source prompt's own "for sensitive documents, capture actor/tenant/document/timestamp/result" instruction (§16) applied selectively, not to every single preview click (which would bloat `audit_log` with pure-read, low-stakes events — the same reasoning PROMPT-027 §52 already used to justify NOT auditing report views). This is a considered, two-tier design, not an oversight: `document_generation_event` = complete, lightweight record of all activity; `audit_log` = the compliance-grade subset.

## 19. GST Document Rules

Already satisfied by construction (§5 principle #5/#8, §8) — GST figures on any print view are the SAME columns the GST/Accounting engines already computed and persisted (PROMPT-011/025/026), never recalculated. The historical-integrity fix (§9) closes the ONE remaining gap (seller/buyer name/address), which is a DISPLAY/identity concern, not a GST-calculation concern — GSTIN itself was already correctly snapshotted before this spec.

## 20. E-Invoice/E-Way Bill Documents

`irn`/`ack_number`/`ack_date`/`qr_code_data` (PROMPT-018) are already the authoritative, integration-result columns — a Sales Invoice print view (§6, newly built) displays them AS-IS, never fabricating a value when `einvoice_status` is not `GENERATED` (the print view must render an accurate "E-Invoice: Not Generated" / "E-Invoice: Failed" state rather than omitting the section entirely, per §19's own "must clearly represent the transaction's actual status" instruction). QR CODE RENDERING (turning `qr_code_data`'s raw string into an actual scannable QR image) is **not implemented** — no QR-rendering library exists in this codebase — flagged as Open Decision #20, the raw string can be displayed as text for M1.

## 21. Payslip Rules

**Already the best-grounded document type in this entire spec** — `payroll_record`/`payroll_record_line` (PROMPT-029) already snapshot everything §21 asks for (`employee_code_snapshot`/`employee_name_snapshot`/`designation_snapshot`, earnings/deductions lines, gross/net). The ONLY new work is building an actual PRINT view (`PayslipPrintPreview`, using the shared shell §10) — `PayslipModal` (PROMPT-029) already exists as an ON-SCREEN modal but has no print/download path today (confirmed — it's a plain modal, no `window.print()` call found in `PayrollManagement.tsx`). No PF/ESI/TDS content is added (§21's own instruction, and structurally impossible anyway — those fields don't exist in the schema at all, PROMPT-029). Access: inherits `payroll.view_payslip` (already exists, PROMPT-029's own stricter permission set).

## 22. Report Export Rules

Reaffirms, does not change, PROMPT-027's own position: report export (where it exists) calls the SAME `app/services/reports/*.py` method the screen itself calls — no separate export-time calculation. PDF/Excel export for reports remains NOT built (Open Decision #8/#9/#10, JSON-only stays the M1 answer, consistent with PROMPT-027 §62's own already-documented OD-018/019/020).

## 23. Notification Architecture

**A genuinely new capability — `ToastContext` today is NOT a notification framework** (confirmed: it holds exactly ONE ephemeral message at a time, auto-dismisses after 5 seconds, has no persistence, no read/unread state, no history, is not tied to any backend event). This spec's new `notification` table + `NotificationService`:

```python
class NotificationEventType(str, Enum):
    SALES_INVOICE_POSTED = "SALES_INVOICE_POSTED"
    PAYMENT_POSTED = "PAYMENT_POSTED"
    PAYROLL_FINALIZED = "PAYROLL_FINALIZED"
    EINVOICE_GENERATED = "EINVOICE_GENERATED"
    EINVOICE_FAILED = "EINVOICE_FAILED"
    EWAY_BILL_GENERATED = "EWAY_BILL_GENERATED"
    EWAY_BILL_FAILED = "EWAY_BILL_FAILED"
    SYNC_FAILED = "SYNC_FAILED"                 # bridges PROMPT-028's own client-side Sync Center
    GST_SUBMISSION_RESULT = "GST_SUBMISSION_RESULT"  # reserved — no real submission exists yet (PROMPT-026)
    DOCUMENT_GENERATION_FAILED = "DOCUMENT_GENERATION_FAILED"  # rare, client-side rendering failure
    # Administrative (once PROMPT-030 ships)
    TENANT_STATUS_CHANGED = "TENANT_STATUS_CHANGED"
    SUPPORT_ACCESS_STARTED = "SUPPORT_ACCESS_STARTED"
```

**Channel-agnostic by design, but ONLY `IN_APP` is enabled in M1** (§23's own instruction, Open Decision #11/#12/#13/#14 resolved as "excluded, not silently built") — no email/SMS/WhatsApp/push integration exists or is added; the `notification` table's own `channel` column is present for future extensibility but always written as `'IN_APP'` today.

**Trigger point**: notifications are created SERVER-SIDE, from WITHIN the same service method/transaction that already calls `AuditService.record(...)` for that action (e.g. `sales_invoice_service.post_invoice` gains one more line: `NotificationService(session).create(...)`) — never a separate, client-inferred event. This mirrors the exact "same transaction, not a parallel weaker path" discipline PROMPT-031 §25 already established for audit writes.

## 24. Notification Authorization

A notification is written with an EXPLICIT `recipient_user_id` (or, for a role-wide notification like "Payroll Finalized," one row PER eligible recipient — determined server-side at creation time by querying which users in the tenant currently hold the relevant permission, e.g. `payroll.view`) — **never a broadcast-then-filter-at-read-time model**, which would risk a client-side leak. This directly satisfies §26's Salesperson/Payroll example: a Salesperson simply never gets a row created for them in the first place, so there is no notification to leak even if the API had a bug — the authorization decision is made once, at write time, by the SAME permission-check logic the rest of the codebase already uses (`ROLE_DEFAULT_PERMISSIONS`/effective permission lookup), not duplicated read-time logic.

## 25. Deduplication

A new unique constraint, `(tenant_id, event_type, entity_type, entity_id)` on `notification` (nullable `entity_id` handled via a partial unique index, same technique already used elsewhere in this codebase for nullable-column uniqueness, e.g. `payment.client_transaction_id`) — a retried IRN-generation attempt that eventually succeeds writes/upserts ONE notification per (tenant, event, entity), not three. This reuses the EXACT idempotency-key-style pattern (natural key, not a client-supplied token) already proven throughout this codebase (`journal_entry`'s own `(tenant_id, source_type, source_id, posting_event_type)` unique constraint, PROMPT-025 — the identical shape, applied here).

## 26. Retry Handling

Given notifications are written server-side, synchronously, within an already-atomic business transaction (§23's trigger point) — **there is no separate "notification delivery" retry loop to design for M1**, since IN_APP delivery IS the database write itself (no external channel, no delivery failure mode beyond the DB write itself failing, which would already roll back the whole transaction — same reasoning as PROMPT-031 §25's audit-atomicity argument, applied identically here). Retry handling becomes relevant ONLY if/when a real external channel (email/SMS) is added later — explicitly deferred, not built now (Open Decision #11-14).

## 27. API Specification

| Method | Path | Auth | Notes |
|---|---|---|---|
| GET | `/api/v1/notifications` | Tenant session | Own notifications only (`recipient_user_id = caller`), paginated, filterable by `read`/`event_category`/`severity` |
| GET | `/api/v1/notifications/{notificationId}` | Tenant session | 404 if not the recipient (same anti-enumeration shape as every other by-ID fetch) |
| POST | `/api/v1/notifications/{notificationId}/read` | Tenant session | Idempotent — marking an already-read notification read again is a no-op, not an error |
| POST | `/api/v1/notifications/read-all` | Tenant session | Bulk, scoped to caller's own notifications only |
| POST | `/api/v1/documents/{entityType}/{entityId}/log-generation` | Tenant session | **New, minimal** — the frontend calls this once per preview/print/download action to populate `document_generation_event` (§17.1); NOT a document-generating endpoint itself, since generation is entirely client-side (§12) |

**Explicitly NOT built**: `GET /documents/{documentId}`, `GET /documents/{documentId}/preview`, `GET /documents/{documentId}/download`, `GET /document-jobs/{jobId}` — all of these assume a persisted document/job model this spec deliberately does not adopt (§16/§7). If a future server-side rendering engine is added, THESE endpoints would be built then, against a real stored artifact — building them now against nothing would be a placeholder with no real behavior, which this codebase's own established discipline (never build a stub that could be mistaken for a real capability, e.g. `SandboxSimulatorProvider`'s "fail loudly" precedent) argues against.

## 28. Database Impact

Two new tables only (both new, both additive — reusing existing structures everywhere possible per §32's own instruction):

1. **`document_generation_event`** (§17.1) — NOT `document`/`document_template`/`document_template_version`/`document_generation_job`, all four explicitly considered and rejected for M1 given no persistence/versioning/async need exists (§11/§16/§7).
2. **`notification`** — `id`, `tenant_id`, `recipient_user_id`, `event_type`, `event_category`, `severity` (`INFO`/`SUCCESS`/`WARNING`/`ERROR`/`CRITICAL`), `title`, `message`, `entity_type`, `entity_id` (nullable), `related_url` (nullable, a frontend route path, never a raw document URL per §12's own constraint), `is_read`, `read_at`, `created_at`.

`document_generation_job` is NOT created (no async generation, §7). `document_template`/`document_template_version` are NOT created (no versioning, §11).

## 38. Risks

- **The historical-integrity fix (§9) cannot be retroactively applied to already-existing invoices** — only NEW invoices going forward get real snapshot data; existing rows must fall back to a live join with an honest UI disclosure ("Historical record — current customer details shown") rather than silently presenting live data as if it were the original. This is a genuine, permanent limitation of adding the fix AFTER the fact, not a defect in the fix itself — must be communicated clearly to the Product Owner, not glossed over.
- **Migrating the 4 existing Purchase-side print components onto the new shared shell (§10) risks a visual/behavioral regression** in already-shipped, already-tested functionality — should be done incrementally with the existing PROMPT-020-023 test coverage re-run after each migration, not as one big-bang rewrite.
- **The `PrintPreviewModal`'s live-`currentTenant`-profile bug** (Requirement Conflict #1, below) has presumably been "working as observed" in every demo/test so far simply because no tenant has ever changed its business profile between creating and re-printing a Purchase Order in this session's own testing — meaning the bug has never actually surfaced, which is exactly the kind of latent defect that could embarrass a user during a real audit. Worth prioritizing the fix despite it appearing "minor."
- **A notification created for every eligible recipient (§24) could create write amplification** for a tenant with many Owner/Manager users on a high-frequency event (e.g. every Sales Invoice post) — acceptable at MVP scale (a handful of users per tenant), flagged as a scaling consideration, not a blocker.
