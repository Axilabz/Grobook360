📘 Accounting & GST Engine — Data Flow

Index Sales Purchase Payments Inventory Payroll Accounting/GST Reports
Every chain on the other pages ends by calling into ONE of these two engines. Neither engine is ever called directly by a frontend screen or API endpoint — both are internal services, invoked only from WITHIN another document's own posting/confirm method, in the same DB transaction.
Engine 1 AccountingPostingService → JournalService
Every posting rule resolves through ONE generic double-entry engine
Called From
  • Sales: Invoice, Return, Credit/Debit Note
  • Purchase: Invoice, Return
  • Payments: Customer Receipt/Supplier Payment post+reverse
  • Payroll: Finalize Run
  • Inventory: 4 Manual stock actions
Entry Points
post_sales_invoice()post_purchase_invoice()post_payment()post_payroll_run()post_opening_stock()post_stock_increase/decrease()

Each builds list[JournalLineInput] from the caller's OWN already-calculated totals — never recomputes GST/amounts itself.

Core Engine
JournalService.post_journal()

app/services/accounting/journal_service.py — validates total_debit == total_credit > 0, resolves each line's posting_rule_code to a real account via ChartOfAccountsService.resolve_account().

Database
journal_entryjournal_linechart_of_accountaccount_mapping

Idempotent on (tenant_id, source_type, source_id, posting_event_type) — a DB unique constraint, checked before insert AND caught as a race-safe backstop.

Side-Effects

Engine 2 GstReportingService → gst_transaction ledger
One sign convention makes period SUM() correct with zero bucket-type special-casing
Called From
  • Sales: Invoice, Return, Credit/Debit Note
  • Purchase: Invoice, Return

Never from Payments, Payroll, or Inventory

Entry Points
record_invoice_transaction()record_return_transaction()record_credit_debit_note_transaction()record_purchase_invoice_transaction()record_purchase_return_transaction()

app/services/sales/gst_reporting_service.py — ONE file serves BOTH Sales and Purchase GST, despite its path.

Sign Convention

Positive: Sales Invoice, Debit Note, Purchase Invoice (increases GST position)

Negative: Sales Return, Credit Note, Purchase Return (decreases it)

Database
gst_transactiongst_transaction_line

Idempotent on (tenant_id, source_type, source_id, event_type). The ORIGINAL row is never edited — even if the product's own gst_rate changes later, the snapshot stays frozen.

Side-Effects
Audit

GST_TRANSACTION_CREATED/GST_TRANSACTION_REVERSED audit entries, scoped to the source document.

Zero import of JournalService/AccountingPostingService anywhere under app/services/gst/ — the two engines are structurally independent, never calling each other directly.

↓ GSTR-1/GSTR-3B/Dashboard/Reconciliation are all computed ON DEMAND from gst_transaction by GstrService (app/services/gst/gstr_service.py) — no persisted "GST Return" entity, no DRAFT/SUBMITTED status anywhere
⚠ No COGS/Inventory journal leg exists for the Sales/Purchase chains — Purchase Invoice still posts to "Purchase Expense" (5010), not "Inventory" (1090). The new INVENTORY/STOCK_ADJUSTMENT/OPENING_BALANCE_EQUITY accounts are used ONLY by the 4 Manual Inventory actions (see the Inventory page) — this is a deliberate, narrow scope decision, not an oversight.
