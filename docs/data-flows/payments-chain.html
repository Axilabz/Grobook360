Customer Receipt (money IN) and Supplier Payment (money OUT) are two thin, direction-specific routers sharing ONE underlying Payment/PaymentAllocation model and ONE PaymentService — §2's own central rule: a payment is never the same record as how it's applied to an invoice. Neither direction ever touches the Stock Ledger or GST — this chain is pure Accounts Receivable/Payable settlement.
1 Create & Allocate (DRAFT)
A DRAFT payment has zero financial effect — allocation here is a non-authoritative preview

CustomerReceiptManagement.tsxSupplierPaymentManagement.tsx

Pick party → amount → allocate across that party's outstanding invoices (an "allocate oldest first" shortcut, server stays authoritative). Also reachable pre-filled from a Sales Invoice's own "Record Collection" action.

Routers: app/api/v1/customer_receipts.py, supplier_payments.py — both thin wrappers over the same service.

app/services/payments/payment_service.py — one service backs BOTH directions (party_type distinguishes them).

2 Post
Row-locks every touched invoice (sorted, deadlock-safe) and re-validates live outstanding under that lock
Frontend
ReceiptDetailModal / payment detail

"Post Receipt"/"Post Payment" confirm dialog.

API Endpoint
POST /customer-receipts/{payment_id}/postPOST /supplier-payments/{payment_id}/post
Service Method
PaymentService.post_payment()

Locks every DISTINCT invoice the allocation touches, sorted by id (PROMPT-022's own deadlock-avoidance pattern, reused verbatim).

Database
paymentsales_invoicepurchase_invoice

Status → POSTED. paid_amount/payment_status recalculated on each touched invoice from SUM(payment_allocation.allocated_amount) across currently-POSTED payments only.

Side-Effects
Accounting

AccountingPostingService.post_payment() — Customer Receipt: DR Cash/Bank/UPI/Cheque (by payment_method) / CR Accounts Receivable. Supplier Payment: mirror image (DR Accounts Payable / CR Cash-Bank-side account).

No Stock Ledger, no GST — ever.

↓ Two ways back to pre-posted state, both reuse the SAME mechanism
3 Reverse (manual) / Cheque Bounce (automatic)
A status flip on the SAME row — never a new compensating record, never an edit
Frontend
"Reverse" button, or "Mark Bounced" on a CHEQUE payment
API Endpoint
POST /customer-receipts/{id}/reversePOST .../cheque-status (+ supplier-payments equivalents)
Service Method
PaymentService.reverse_payment()mark_cheque_status()

A BOUNCED transition internally calls reverse_payment() — no separate exclusion path exists.

Database
payment

Status → REVERSED. payment_allocation rows are NEVER deleted — the recalculation simply stops counting a non-POSTED payment's allocations, restoring outstanding on every invoice it touched.

Side-Effects
Accounting

AccountingPostingService.reverse_payment() → JournalService.reverse_journal_for_source() — a brand-new journal with debit/credit swapped; the original journal is never edited.
